# HW4: надійність і безпека

## Тема 7: fallback і деградація

У режимі mock сервіс пробує модель, обрану маршрутизатором, а після `429`,
`5xx` або мережевого збою — інший mock-аліас. Кожен перехід збільшує атомарний
лічильник і записується в журнал із `request_id`. Якщо резервна модель відповіла,
в `requests.model` записується саме вона. Якщо всі спроби не вдалися, API
повертає ввічливу заглушку, а в лог записується статус останнього збою.
Коли білінг хоча б однієї спроби невідомий, загальна вартість — `NULL`.
Заглушка й відповідь резервної моделі не зберігаються за ключем основної моделі.

Обидва mock-аліаси ведуть до одного процесу, тому це перевірка механіки, а не
резервування незалежного провайдера. Для явно заданої реальної моделі автоматичного
резерву не налаштовано. Retry з backoff та circuit breaker не реалізовані.

Перевірка: `docker compose up -d --build service`, потім
`python3 -m unittest discover -s tests -p test_hw4_reliability.py -v`.
Тест успішної резервної спроби запускає окремий сервіс із тестовим HTTP gateway
на хості та використовує адресу `host.docker.internal` у Docker Desktop.

Для аналізу інциденту лог має дати відповіді: скільки було переходів на резерв,
який маршрут повернув успішну відповідь і які запити завершилися помилкою навіть
після переходу.
