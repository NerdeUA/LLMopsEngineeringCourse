# Перевірка HW1 за повним текстом Теми 2

Джерело: [Тема 2. Prompt lifecycle: промпт як production-артефакт](https://www.edu.goit.global/learn/53769072/54507483/55047070/training).
Прочитано всі 7 розділів і 19 текстових елементів, включно з матеріалом за
кнопками продовження. Виявлений у frontend параметр GET `next` дав змогу
отримати повний текст, а не лише першу порцію кожного розділу.

## Відповіді на шість пунктів «Перевірте себе»

1. **Де зберігається робочий промпт?** У `prompts.body` в PostgreSQL. `v1` та
   `v2` створюються в `db/schema.sql`. `ReadActivePrompt` читає активну пару
   текст/версія для кожного запиту. Робочої support-копії в коді немає;
   передбачений завданням запасний загальний промпт залишається в коді.
2. **Чи фіксується використана версія?** Так. Та сама локальна `promptVersion`,
   яку отримано разом із текстом, передається до `LogRequest` і записується
   в `requests.prompt_version`. Пізніша активація не змінює історичні рядки.
3. **Чи відтворюється погіршення та відкат?** Так. Активація `v1` змінює відповідь
   на «не знаю» й дає eval 3/6, exit 1 при порозі 5. Повернення `v2` відновлює
   відповідь та eval 6/6, exit 0 без перезапуску сервісу.
4. **Що буде при помилці в назві версії?** `POST /prompts/v99/activate` повертає
   `404`; поточна активна версія зберігається. Перевірка існування і перемикання
   виконуються в одній транзакції. Блокування та частковий унікальний індекс
   також забезпечують одну активну версію при конкурентних активаціях.
5. **Що буде без активної версії?** Коли БД доступна, але всі `active=false`,
   використовується `You are an assistant.`. Mock відповідає «не знаю»,
   у журналі — `none`. Після перевірки відновлюється `v2`.
6. **Чи працює картка реєстру?** Так. `GET /prompts` повертає масив із назвою,
   версією та активністю. Готовий UI показує обидві версії, активну позначку
   й кнопку активації біля неактивної. Скриншоти є у PR та `docs/screenshots/`.

## Уточнення з повного тексту

У лабораторній роботі прямо розрізняються порожній реєстр та інфраструктурний
збій. Початкова реалізація HW1 маскувала недоступність PostgreSQL запасним
промптом і відповіддю HTTP 200. Це підтвердив новий інтеграційний тест на окремому
контейнері сервісу з недоступним підключенням, без зупинки основної БД.

Виправлення: при помилці читання БД `/chat` повертає `503` та записує помилку
з ідентифікатором запиту в журнал процесу. Запасний промпт `none` залишається
для доступної БД без активної версії. Після виправлення обидва сценарії мають
окремі тести.

Назва промпта в нашому проєкті — `support`; SQL-приклади уроку використовують
`support-system`. Семантика однакова, але в ручних SQL-перевірках цього проєкту
потрібно підставляти `WHERE name = 'support'`.

Транзакційне перемикання двома UPDATE з блокуванням відповідає вимозі
атомарності: зовнішні читачі не бачать проміжного стану. Сам текст теми також
пояснює еквівалентність спільної транзакції та однієї атомарної операції.

Після виправлення `python3 -m unittest discover -s tests -v`: **13/13 passed**
(6 HW1, 6 HW2 та окрема перевірка недоступної БД). Нова перевірка спочатку
відтворила помилку HTTP 200, а після виправлення підтвердила `503` та запис
у журналі процесу. Незалежне рев'ю не виявило суттєвих проблем.

## Що ще важливо розуміти

- Мітка версії відповідає незмінному тексту: правки оформлюються новою версією.
- Роль, правила, формат і few-shot-приклади разом утворюють системний промпт.
- Дані користувача передаються окремим `user`-повідомленням, не додаються до
  `system`. Це зменшує неоднозначність, але повний захист від ін'єкцій — тема 8.
- Git показує зміни коду, а `prompt_version` — фактично використаний промпт.
- GROUP BY за версією дає операційне порівняння; A/B-тест потребує стабільного
  розподілу трафіку та заздалегідь визначених метрик.
- Хто й коли перемикав версію, показує окремий журнал активацій. Він опційний
  і наразі не реалізований; `created_at` у `prompts` є часом створення версії.
