# HW3: кеш + інструменти

Після уроків 5–6.

Що маєш отримати в кінці: на однакове питання вдруге система відповідає з кешу,
не ходячи в модель, і вміє виконати дію (інструмент), коли модель про це просить.

## Завдання

1. **Кеш відповідей.** Однаковий запит удруге не йде в модель.
   Ключ кешу — модель + промпт + повідомлення (усі три, не лише повідомлення).
   Рахуй окремо попадання (hit) і промахи (miss) — ці лічильники потім підуть
   на плитку в консолі.

2. **Інструменти.** Коли модель повертає tool_call `lookup_order`, виконай його
   і встав результат у відповідь користувачу.

3. **Два рішення словами, в описі PR.** Коду тут не треба — по 1–2 речення
   на кожне:
   - Який timeout ти поставив би на виклик інструмента і чому.
   - Як не виконати дію двічі, якщо виклик повторився (це і є ідемпотентність).
     Найпростіший ключ — `request_id`: другий виклик із тим самим id ігнорується.
     Допиши, від чого він **не** рятує: якщо модель попросить те саме наступним
     ходом або користувач двічі натисне кнопку — `request_id` буде вже інший.
     Тут допоміг би ключ від самої дії, наприклад
     `hash(conversation_id, tool_name, args)`. Робити його не треба — лише згадати.

   Якщо опис PR може загубитися (перездача, squash) — продублюй ці два рішення
   в README, розділ «Операційні рішення».

## Перевір себе

1. Напиши боту одне й те саме питання двічі. Потім:
   `SELECT latency_ms, prompt_tokens, completion_tokens, cost_usd FROM requests ORDER BY created_at DESC LIMIT 2;`
   У свіжішого рядка токени і `cost_usd` мають бути нульові.
   Не орієнтуйся на `latency_ms`: на mock промах теж займає 9–16 мс.
2. Напиши те саме питання ще раз (воно в кеші), потім `POST /prompts/v1/activate`,
   потім знову те саме питання. Має бути **промах**: `prompt_tokens > 0`,
   `prompt_version = v1`. Промпт змінився — кеш не має віддавати стару відповідь.
   Поверни `v2`.
3. «Де моє замовлення #123?» — у відповіді є фактичний статус замовлення,
   а не лише «перевіряю».

## Опційно (не оцінюється)

- TTL: старі записи кешу протухають і перезапитуються.
- Semantic cache: порівняння за схожістю, а не точним збігом. Redis для цього
  піднімається командою `docker compose --profile advanced up`.
- Перевірка аргументів: tool_call без обов'язкового аргументу → запис про відмову
  в лозі, а не виконання. Mock шле порожні `arguments`, тож перевіряти юніт-тестом
  (як завести тест-проєкт — GETTING_STARTED §10).
- Реалізувати timeout на інструмент. Маркер `__delay` затримує відповідь **моделі**,
  а не інструмента, тому ним цей timeout не перевірити — лише юніт-тестом.

## Що здаєш

PR, де другий однаковий запит відповідає з кешу, а «Де моє замовлення #123?»
повертає результат інструмента.

## Критерії перевірки

| Що | Як | Очікується |
|---|---|---|
| Повтор не пішов у модель | два однакові запити → два свіжі рядки `requests` | у свіжішого `prompt_tokens = 0`, `completion_tokens = 0`, `cost_usd = 0` |
| Промпт входить у ключ кешу | питання з кешу → activate `v1` → те саме питання → свіжий рядок | промах: `prompt_tokens > 0`, `prompt_version = v1` |
| Лічильники кешу | код `/chat` або лог | hit і miss рахуються окремо |
| Інструмент | «Де моє замовлення #123?» | у відповіді фактичний результат |
| Два рішення | опис PR або README | timeout і ключ ідемпотентності названі й пояснені |
| Evals | прогін | зелені |

## Навіщо це в реальній системі

Кеш — це рішення про коректність, а не про швидкість: у мультитенантних системах
ключ без тенанта означає, що два клієнти з однаковим питанням отримають одну
відповідь — це вже витік, а не оптимізація. А timeout та ідемпотентність тут не
«best practice для галочки»: на платформі, яку я супроводжую, ланцюг таймаутів
tool-викликів довелося редизайнити окремим проєктом, бо рівні розжилися
суперечливими лімітами — і завислий виклик з'їдав бюджет усього запуску.
