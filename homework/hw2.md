# HW2: routing + cost

Після уроків 3–4.

Що маєш отримати в кінці: система сама обирає модель під тип питання і знає,
скільки коштував кожен запит.

## Завдання

1. **Routing — вибір моделі за питанням.** Мінімум два маршрути:
   - звичайні питання → `mock-mini`;
   - повернення, скарги, «терміново» → `mock-strong`.

   Обидві моделі вже описані в `gateway/litellm-config.yaml`. Ключові слова
   для розпізнавання — і українські, і англійські.

2. **Cost — вартість запиту.** Заведи табличку цін за 1k токенів для кожної моделі
   і рахуй вартість кожного запиту в поле `cost_usd` у `requests`.

3. **`GET /cost`** — віддає `{ today_usd, budget_usd }`. Консоль покаже плитку
   «Вартість сьогодні».

4. **Запиши запасний порядок моделей.** Біля коду роутера — константа або коментар:
   яка модель підхоплює, якщо основна впала. Наприклад:
   `// fallback chain: mock-strong -> mock-mini -> заглушка`.
   Поки що це лише запис; код, який по ньому перемикається, — у hw4.

## Перевір себе

1. Напиши боту звичайне питання, потім «поверніть гроші терміново».
   Кирилицю в Git Bash відправляй із файлу: `--data @file.json`, інакше маркери
   не спрацюють.
2. `SELECT model, count(*) FROM requests GROUP BY model` — дві різні моделі.
3. `SELECT cost_usd FROM requests WHERE cost_usd > 0 LIMIT 3` — є значення.
4. `GET /cost` → `today_usd` збігається з
   `SELECT round(SUM(cost_usd), 4) FROM requests WHERE created_at::date = CURRENT_DATE`.
5. Плитка «Вартість сьогодні» на mock показує `$0.00` — це нормально, консоль
   округлює до центів. Чесність плитки перевіряється через `GET /cost`, не через цифру.

## Опційно (не оцінюється)

- Бюджет: при 80% витрат — попередження в лог або перемикання на дешевшу модель.
- Третій маршрут: окремий tier для FAQ, ескалацій і «всього іншого».

## Що здаєш

PR, де в `requests` різні моделі для різних питань, заповнений `cost_usd`,
плитка вартості в консолі жива.

## Критерії перевірки

| Що | Як | Очікується |
|---|---|---|
| Routing працює | звичайне питання англійською + «поверніть гроші терміново» → `GROUP BY model` | дві різні моделі |
| Cost рахується | `SELECT cost_usd FROM requests WHERE cost_usd > 0 LIMIT 3` | є значення |
| Ціна залежить від моделі | `SELECT DISTINCT model, round(cost_usd/(prompt_tokens+completion_tokens), 9) AS unit FROM requests WHERE cost_usd > 0;` | у `mock-strong` ціна за токен на порядок вища |
| Запасний порядок записаний | код біля роутера | константа або коментар із повним порядком |
| `GET /cost` | виклик | `today_usd > 0` |
| `GET /cost` не бреше | порівняти з `SUM(cost_usd)` за сьогодні | збігається |
| Evals | прогін | зелені |

Деталі — [CHECKS.md](CHECKS.md#hw2).

## Навіщо це в реальній системі

Найбільший важіль вартості — не «дієта» промпта, а те, що дороге дістається лише
складному: різниця між дешевою і сильною моделлю — порядок, а не відсотки.
І маршрутизувати треба не лише запити користувачів: на одній агентній платформі
найжирнішим споживачем виявився службовий LLM-виклик усередині кожного запуску —
його свідомо перевели на дешеву модель без утрати якості. Прайс при цьому — живі
дані: ми ловили в каталозі ціни, що вже розійшлися з тарифами постачальника,
і виправляли їх як баги.
