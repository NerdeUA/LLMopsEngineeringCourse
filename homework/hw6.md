# HW6: CI-гейт + інцидент

Після уроків 11–12. Це фінал: система зібрана.

Що маєш отримати в кінці: PR зі зламаним промптом не можна змержити, бо CI
червоний; у репозиторії лежить сценарій інциденту, який відтворюється командами;
у README — план, як перенести практики курсу у свою команду.

## Завдання

1. **Увімкни eval-гейт у CI.** Шаблон `.github/workflows/eval-gate.yml` уже є:
   на кожен PR піднімається стек і ганяються evals. Постав у workflow той самий
   `--threshold`, що ти вивів у hw5 — він має збігатися з локальною командою.

   Щоб червоний чек справді **блокував** merge, увімкни branch protection:
   Settings → Branches → Add branch protection rule → Require status checks
   to pass → обери чек **`eval`**. Увага: GitHub показує назву **job** (`eval`),
   а не workflow (`eval-gate`). Якщо обереш неіснуючий `eval-gate` — protection
   нічого не блокуватиме.

   На приватному репо безкоштовного плану protection може бути недоступний.
   Тоді напиши про це в описі PR: гейт «радить», а не блокує.

2. **Покажи, що гейт ловить.** Зламай промпт навмисно (наприклад, зроби `v1`
   активним у міграції) — CI червоний. Потім поверни — зелений. Де це робити —
   на твій вибір: окремим комітом у фінальному PR і потім revert, або окремим
   demo-PR, який закриваєш без мержа. Головне — обидва прогони в історії Actions.
   Як це виглядає — відео уроку 11.

   > Якщо GitHub Actions недоступний (корпоративна політика, GHE без Actions):
   > прожени ті самі кроки локально — підняти стек → evals → подивитись exit code —
   > і додай у PR позначку «CI не запускався: Actions недоступні» з виводом прогону.
   > Це неповне закриття тижня: merge нічим не блокується.

3. **`INCIDENT_RUNBOOK.md`** у корені репозиторію, з посиланням із README.
   Сценарій «інцидент → fallback → відновлення» і команди, які відтворюють його
   **дослівно** — з реальним хостом, без `...`.
   «Відновлення» означає: після серії збоїв звичайне питання знову відповідає
   нормально, а в консолі видно сплеск `fallback_events` і спад `error_rate_pct`
   (`fallback_events` лише зростає, він не спадає ніколи — тому спад видно саме по error rate).
   Питання на кроці відновлення — **нове**, якого ще не було в кеші. Інакше кеш
   віддасть стару відповідь, і «відновлення» виглядатиме успішним посеред інциденту.

4. **Розділ «30-day rollout» у README.** Чотири кроки, як перенести практики курсу
   у свою команду, по одному реченню на крок. Кожен крок — практика курсу +
   конкретна дія у твоїй команді. Начерк є з лаби уроку 12 — доведи до чотирьох
   чітких кроків.

## Перевір себе

1. Клонуй свій репозиторій у чисту папку і запусти `docker compose up --build`.
   Система працює, консоль жива. Робочий стек курсу перед цим згаси
   (`docker compose down` у робочій теці), інакше порти займе він. Або піднімай
   клон із зсунутими портами:
   `docker compose -f docker-compose.yml -f demo-ports.yml up --build -d`.
2. В Actions є червоний і зелений прогін.
3. `grep -n "continue-on-error" .github/workflows/eval-gate.yml` — нуль рядків.
4. `gh api repos/<owner>/<repo>/branches/main/protection --jq '.required_status_checks.contexts'`
   — у списку є `eval`.
5. Команди з `INCIDENT_RUNBOOK.md` виконуються як написано і показують fallback
   і відновлення.

Якщо гейт червоний з незрозумілої причини — три типові граблі з уроку 11:
(1) цикл очікування без `if curl; then` вбивається `bash -e`;
(2) холодний gateway віддає 500 на перший запит — потрібен окремий wait-крок;
(3) перевірка «код == 200» замість діапазону.
Понад 1.5 години дебагу — здай лог червоного прогону зі своєю гіпотезою
і добий після рев'ю.

## Опційно (не оцінюється)

- Canary-план: як роутером розділити трафік 90/10 між двома версіями промпта
  і за якими метриками вирішувати promote / rollback.
- `/metrics` + зовнішній дашборд (Redis і дашборди піднімаються командою
  `docker compose --profile advanced up`).

## Що здаєш

Фінальний PR: система збирається `docker compose up`, плитки живі, в історії CI
є червоний і зелений прогін, `INCIDENT_RUNBOOK.md` із посиланням із README,
розділ «30-day rollout».

## Критерії перевірки

| Що | Як | Очікується |
|---|---|---|
| Гейт є | вкладка Actions | прогони eval-gate на PR |
| Гейт ловить | історія CI | червоний (злам) і зелений (фікс) |
| Гейт живий зараз | зламати промпт у PR → revert; `grep continue-on-error`; `gh api … protection` | червоний → зелений; grep нуль; contexts містить `eval` |
| Інцидент відтворюється | виконати `INCIDENT_RUNBOOK.md` | fallback і відновлення видно; питання відновлення нове |
| Чиста збірка | `docker compose up --build` з чистого клону | працює, консоль жива |
| Поріг гейта | `--threshold` у workflow + README | збігається з локальним, не нижче правила з hw5, пояснений |
| 30-day rollout | README | 4 конкретні кроки |

## Навіщо це в реальній системі

Гейт цінний рівно настільки, наскільки він здатний бути червоним. У пайплайні
одного сервісу довго жила обгортка, що «м'якшила» quality gate: крок виконувався,
а його негативний результат не валив збірку — зелений колір був, захисту не було;
прибирали як баг. Тому перевірка вашого гейта — не «крок є», а «зламав навмисно →
merge заблокований». І друге: автоматика, що робить незворотне, виходить першим
релізом у режимі dry-run — проходить повний цикл і пише звіт «що я б зробила»;
запобіжник знімають після кількох днів читання звітів.
