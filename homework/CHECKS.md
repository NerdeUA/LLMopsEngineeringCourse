# Як саме перевіряються ДЗ: нюанси й контрприклади

Таблиці «Критерії перевірки» у `hwN.md` — короткі. Тут — що саме ментор вважає
провалом у кожному рядку, які «майже правильні» рішення не проходять і чому.
Критерії не змінюються всередині потоку. Читати до здачі не обов'язково;
якщо отримав «на доопрацювання» — читай розділ свого тижня.

Головне правило всіх тижнів: зараховується не наявність коду, а те, що він
справді працює. Кеш, який ніколи не влучає; черга approvals, що є «для звіту»,
а тікет створюється одразу; `/providers`, який завжди віддає `ok`; запасний
промпт, через який не видно поломку реєстру; `continue-on-error` у гейті — усе це
«код є, а властивості немає», і саме це ловлять негативні рядки таблиць.

Два терміни, які трапляються нижче: **core-доріжка** — обов'язкова частина ДЗ,
без опційного; **кумулятивна перездача** — PR, у якому крім поточного тижня
є і попередні.

## hw1

- **Промпт у БД.** У відповіді `GET /prompts` має бути видно, котра версія активна
  (поле `active` чи еквівалент). Список версій без ознаки активної — на доопрацювання.
- **Версії заведені міграцією.** `docker compose down -v && docker compose up --build`, потім
  `docker compose exec postgres psql -U llmops -d llmops -c "SELECT name, version, active FROM prompts"`
  → два рядки, `active` рівно один — без жодного ручного `INSERT`. Seed сидить
  у `db/schema.sql`, а не в коді сервісу. Швидка перевірка джерела:
  `grep -ri "INSERT INTO prompts" service/` → нуль влучань.
- **Версія в лозі.** `prompt_version` у свіжому рядку мусить **збігатися з активною
  версією реєстру**. Непорожність недостатня: константа в лозі цей рядок не проходить.
- **Зламаний реєстр видно.** `UPDATE prompts SET active=false;` → `POST /chat`.
  Обов'язкові **обидві** умови («і», не «або»): відповідь змінилась («не знаю» або
  власний запасний текст) **і** `prompt_version` у лозі ≠ версія з реєстру
  (в еталоні — `none`). Провал будь-якої половини — на доопрацювання:
  нормальна support-відповідь із `prompt_version=v2` — замаскована поломка; але й
  нормальна support-відповідь із чесним `none` — теж маскування (запасний промпт
  підміняє реєстр непомітно для користувача).
- **Rollback ловиться evals.** Команда і поріг стартового датасету — `--threshold 5`
  (GETTING_STARTED §6); цей поріг чинний для hw1–hw4, поки датасет стартовий.
  На `v1` прогін має бути **нижче порога** (exit 1; еталонна картина — 3/6),
  на `v2` — зелений. «Один-два червоні кейси при зеленому підсумку» — це не «ловиться».

## hw2

- **Routing.** Перевіряються **обидві мови**: англійське звичайне питання
  («How do I reset my password?») і українська ескалація («поверніть гроші
  терміново»). Роутинг на ключових словах однієї мови — половина роутера.
  Кирилицю в Git Bash шли з файлу (`--data @file.json`), інакше маркери не спрацюють.
- **Cost рахується.** Фільтр `cost_usd > 0` — бо нульова вартість легальна:
  з hw3 її даватиме cache-hit.
- **Ціна залежить від моделі.** Питома ціна `mock-strong` вища за `mock-mini`
  **на порядок** (в еталоні ~16×), бо ціни беруться з таблички за моделлю.
  Однакова питома ціна або різниця лише в десятки відсотків = пласка ставка
  замість таблички = на доопрацювання.
- **Fallback-порядок.** Саме в **коді** біля роутера; опис у PR — додатково,
  не замість.
- **Консоль.** Готова консоль округлює до центів, тож на mock плитка показує
  `$0.00` — це очікувано; критерій перевіряється через `GET /cost` (`today_usd > 0`).
- **Ендпоінт не бреше.** `today_usd` збігається з
  `SELECT round(SUM(cost_usd), 4) FROM requests WHERE created_at::date = CURRENT_DATE`
  (допуск — запити між двома командами). Розбіжність у рази = ендпоінт віддає
  константу «щоб плитка ожила» = на доопрацювання. `today_usd > 0` сам по собі
  чесність не доводить.

## hw3

- **Повтор не пішов у модель.** Ненульові токени на повторі = кеш не влучає,
  **незалежно від latency**. На mock «< 50 мс» нічого не доводить: промах теж
  коштує 9–16 мс, і здача зовсім без кешу пройде таку «перевірку».
- **Ключ кешу повний.** Те саме питання (воно вже в кеші) → `POST /prompts/v1/activate`
  → повторити → `SELECT prompt_version, prompt_tokens FROM requests ORDER BY created_at DESC LIMIT 1;`
  → повернути `v2`. Мусить бути **промах**: зміна промпта інвалідує кеш, бо промпт
  сидить у ключі. Відповідь із кешу (0 токенів, стара v2-відповідь) = ключ
  рахується лише з повідомлення: rollback-механізм hw1 мовчки зламаний, а зміна
  моделі/промпта більше не змінює відповідей = на доопрацювання.
  Цей рядок ментор повторює і на hw4–hw6, якщо diff зачепив кеш.
- **Інструмент.** У відповіді на «Де моє замовлення #123?» — **фактичний результат**
  (статус замовлення; еталон дописує « (статус: …)»), а не лише намір «перевіряю»
  без даних.
- **Операційні рішення.** Порожній опис PR там, де рядок вимагає опис, — непройдений
  рядок (або дублюй розділом «Операційні рішення» у README). Поведінкова перевірка
  ідемпотентності — у hw4, коли з'явиться черга approvals.

## hw4

- **Fallback-ланцюг.** Перевіряється рев'ю коду, бо на mock обидві спроби падають
  і видимий ефект — лише заглушка. Цикл по ланцюгу з **щонайменше двох** елементів
  (два аліаси з `litellm-config.yaml`) + лічильник, що інкрементується на кожному
  переході. Ланцюг з одного елемента — на доопрацювання.
- **Degradation.** HTTP 200 (не 500); текст власний (не стартерів «Сервіс тимчасово
  недоступний»); **без вигаданого предметного факту** — ні статусу замовлення,
  ні номера тікета, ні «зроблено»: лише чесне «тимчасова проблема, спробуйте
  згодом». Конкретно: у відповіді на `__fail_503` немає ні цифр замовлення,
  ні слова «тікет».
- **Чому повторний approve — `404`, а не `409`.** Заявку споживає approve: після
  виконання її вже немає в черзі, і «вже виконано» та «ніколи не існувало» навмисно
  нерозрізнені, щоб відповідь не підказувала, які id існують. Так поводиться еталон `w4`.
- **Дія не сталася до approve.** Жодного тікета/результату **в обох місцях**:
  ні `result` у `GET /approvals` (заявка pending), ні номера тікета в тексті
  відповіді чату. Номер у відповіді до approve = дія виконана одразу або вигаданий
  факт — обидва ✗. Після одного approve — рівно один; після повторного — той самий
  один і HTTP `404` «already done». Так поводиться еталон `w4`.
- **Guardrail PII.** Два запити, що різняться **лише** email-ом («мій email a@b.com,
  скиньте пароль» / «мій email c@d.net, скиньте пароль», кирилицю з файлу), потім
  `SELECT prompt_tokens FROM requests ORDER BY created_at DESC LIMIT 1;`.
  Другий — **cache-hit** (`prompt_tokens = 0`): маскування спрацювало до обчислення
  ключа. Обидва пішли в модель = ключ рахується з сирого повідомлення, email осідає
  в ключах кешу = на доопрацювання. «До моделі» — рев'ю коду: тіло запиту до моделі
  ніде не логується, це межа стенда, і це чесно названо. Юніт-тест — додаток,
  не заміна цього рядка.
- **Evals після інциденту.** Якщо робив опційний circuit breaker, одразу після серії
  `__fail_503` прогін **червоний** (breaker тримає заглушку) — це правильна поведінка.
  Почекай до закриття breaker'а (~30 с або до half-open-проби) — тоді прогін мусить
  бути зеленим. Ментор про це знає і не повертає за такий червоний.

## hw5

- **Плитки живі.** Перевірка від **свіжого старту сервісу** і після прогріву:
  холодний gateway валить перші запити — без прогріву хибні err=100%, cache-hit=0.
  Cache-hit і fallback живуть у пам'яті процесу й обнуляються при рестарті: одразу
  після `up --build -d service` плитки покажуть requests з БД і нулі в лічильниках —
  очікувано, не дефект.
- **Дані чесні.** Три SQL (requests, error rate, p95 за сьогодні) збігаються
  з плитками; допуски — запити між командами, для p95 ±1 мс округлення.
  Після `__fail_503` `error_rate_pct` **> 0**; плитка error rate = 0 одразу після
  збоїв — прибитий цвях, який зеленіє посеред інциденту = на доопрацювання.
  Те саме для p95: константа замість перцентиля з БД = на доопрацювання.
- **Статус провайдера чесний.** 3× `__fail_503` поспіль → статус ≠ `ok`
  (`degraded`/`down`), картка не зелена. Для core-доріжки (без breaker'а) достатньо
  «`degraded` після N поспіль збоїв ланцюга». Вічне `ok` — на доопрацювання.
- **Власні кейси.** `git diff` по `evals/golden.jsonl` **проти бази PR** (main;
  при кумулятивній перездачі — проти попереднього зарахованого стану). Кейс, що має
  і `expect`, і `forbid`, рахується негативним. Жоден стартовий кейс не видалений.
- **Без фальш-позитивів.** Будь-який зелений кейс під `__fail_503` — на доопрацювання,
  крім `expect_refusal` при вхідному injection-детекті (опційне з hw4), і то
  з поясненням у PR. `expect`-кейс зеленим бути не може.
- **Поріг.** N−1 при N≤10; при N>10 — `ceil(0.85·N)` (N=11 → 10). Значення й причина
  в README.

## hw6

- **Гейт живий на поданому стані.** Обов'язковий мінімум рядка — **живий злам**:
  у PR зламати промпт одним комітом (activate `v1` у міграції або окремий demo-PR)
  → червоний чек → revert → зелений. `grep continue-on-error` і `gh api … protection`
  — додатково; grep сам по собі недостатній: `|| true` у кроці Evals, `if: always()`
  тощо він не ловить. Історія Actions тритижневої давнини рядок **не** закриває —
  перевіряється поточний стан гейта. `contexts` порожній або 404 = protection не
  налаштований → червоний гейт нічого не блокує; легальний виняток — чесна позначка
  «план без protection» у PR.
- **Інцидент-демо.** Задокументована в runbook підстановка зсунутого порту — не
  порушення «дослівності». Питання на кроці відновлення — нове, не з кешу, інакше
  кеш віддасть стару відповідь із `latency_ms=0` і демо зазеленіє посеред інциденту.
- **Фінальна збірка.** З чистого клону. Якщо на машині зайняті стандартні порти —
  `docker compose -f docker-compose.yml -f demo-ports.yml up --build -d`; це не
  порушення «однієї команди».
- **Поріг гейта.** У **двох** місцях — локальна команда і workflow; не нижче правила
  з hw5; занижений без обґрунтування — на доопрацювання.
- **30-day rollout.** Зараховано = кожен крок називає практику курсу + конкретну дію
  у своїй команді. «Впровадимо evals» — ні. «Тиждень 1: golden set на 10 кейсів
  з реальних тікетів нашого саппорту» — так.
