# HW5: observability + evals

Після уроків 9–10.

Що маєш отримати в кінці: усі плитки консолі показують живі числа з бази і
з твоїх лічильників, а якість перевіряється власним набором eval-кейсів, який
справді ловить поломки.

## Завдання

1. **`GET /observability`.** Три числа з таблиці `requests` за сьогодні:
   кількість запитів, p95 latency, error rate. Плюс два з твоїх лічильників:
   cache-hit % (hw3) і кількість fallback-перемикань (hw4).

2. **`GET /providers`.** Статус провайдера для консолі. Він має реагувати на
   збої: після кількох невдач ланцюга поспіль — `degraded`, а не вічне `ok`.

3. **Додай свої eval-кейси.** Мінімум 4 нові кейси в `evals/golden.jsonl`.
   Щонайменше 2 з них негативні — з `forbid` або `expect_refusal`, тобто такі,
   що падають, якщо бот поводиться неправильно. Стартові кейси не видаляй.
   Якщо треба — свій grader у `evals/run.py`.

   Дві підказки:
   - Mock (`mock-provider/Program.cs`, функція `Reply`) розпізнає питання по
     черзі, перший збіг виграє. «Дякую за допомогу» впіймає гілку `допомог`
     раніше за `дякую`. Якщо кейс залежить від конкретної відповіді — підбери
     формулювання або подивись у лозі, що реально повернулось.
   - Корисний кейс — маркер `__garbage`: на нього mock віддає відповідь `...`
     (три крапки, код 200 — формально успіх, по суті сміття). Такий кейс ловить
     категорію «успішна, але непридатна» з уроку 1. Щоб він працював, сервісу
     потрібна невелика доробка: якщо від моделі прийшло `...`, віддати
     користувачу свій чесний текст на кшталт «не зміг сформулювати відповідь,
     спробуйте переформулювати» — окремий від заглушки з hw4. Тоді кейс з `expect`
     на цей текст зелений у нормі і червоний під `__fail_503`.

4. **Перевір, що кейси не проходять «самі по собі».** Зроби копію датасету,
   у кожному `input` допиши на початок `__fail_503 ` і прожени. Результат має бути
   **0 пройдених**. Кейс, що зеленіє, коли система лежить, нічого не перевіряє —
   додай йому `forbid` із фрагментом тексту твоєї заглушки (урок 10, блок 03).

   Виняток: якщо ти робив опційний injection-детект у hw4, кейси з `expect_refusal`
   лишаться зеленими — відмова народжується до виклику моделі. Це правильно,
   поясни одним реченням в описі PR. Кейси з `expect` зеленими бути не можуть.

5. **Підбери поріг evals під свій датасет.** N — кількість кейсів:
   при N ≤ 10 поріг = N−1; при N > 10 поріг = 85% від N з округленням угору
   (N=11 → 10). Значення й пояснення — у README.

## Перевір себе

1. Перезапусти сервіс. Спершу прогрій gateway одним-двома запитами (холодний
   старт валить перші запити — без прогріву побачиш хибні err=100%).
   Потім кілька запитів, включно з повтором і `__fail_503`.
2. У консолі всі 6 плиток з числами: Запити, p95 latency, Error rate, Cache-hit,
   Fallback, Вартість сьогодні. Cache-hit > 0, fallback > 0.
   Cache-hit і fallback живуть у пам'яті процесу і після рестарту починаються
   з нуля — це нормально.
3. Звір плитки з базою:
   - requests: `SELECT count(*) FROM requests WHERE created_at::date = CURRENT_DATE`
   - error rate: `SELECT round(100.0 * count(*) FILTER (WHERE status <> '200') / count(*), 1) FROM requests WHERE created_at::date = CURRENT_DATE`
   - p95: `SELECT round(percentile_cont(0.95) WITHIN GROUP (ORDER BY latency_ms)) FROM requests WHERE created_at::date = CURRENT_DATE`

   Після `__fail_503` error rate має бути більший за 0.
4. Три рази `__fail_503` поспіль → `GET /providers` показує не `ok`, картка не зелена.
5. Копія датасету з `__fail_503 ` у кожному `input` → 0 пройдених.
6. Повний прогін із твоїм датасетом і твоїм порогом — зелений.

## Опційно (не оцінюється)

- Один SLO і бюджет помилок: ціль для показника, який відчуває користувач
  («частка відповідей по суті ≥ 99%»), і скільки невдач це дозволяє на тижневому
  обсязі. Абзац у README (урок 9, блок 07).
- Лічильники помилок за причинами: 429 провайдера, timeout інструмента,
  відмова guardrail.
- LLM-as-judge grader — потребує реального ключа; його виклики теж рахувати
  у вартість.

## Що здаєш

PR, де всі плитки консолі живі (числа, не «—»), evals зелені з розширеним датасетом.

## Критерії перевірки

| Що | Як | Очікується |
|---|---|---|
| Плитки живі | прогрів → кілька запитів (з повтором і `__fail_503`) → консоль | 6 плиток з числами, cache-hit > 0, fallback > 0 |
| Числа чесні | requests, error rate, p95 проти SQL за сьогодні | збігаються; після `__fail_503` error rate > 0 |
| `GET /providers` | виклик + картка | статус є, картка не «—» |
| Статус реагує на збої | 3× `__fail_503` → `GET /providers` | не `ok`, картка не зелена |
| Свої кейси | `git diff` по `golden.jsonl` проти бази PR | ≥4 нові, ≥2 негативні, жодного видаленого |
| Кейси не проходять самі | копія датасету з `__fail_503 ` | 0 пройдених (виняток — `expect_refusal` з injection-детектом, з поясненням) |
| Evals | прогін із твоїм датасетом | зелені; поріг за правилом, пояснений у README |

Деталі — [CHECKS.md](CHECKS.md#hw5).

## Навіщо це в реальній системі

Дві дрібниці вирішують, чи буде що дивитися під час інциденту. Перша: ключові
переходи стану мусять логуватися на рівні, увімкненому в проді — нам довелося
окремим рішенням підняти лайфсайкл-логи з debug до info, бо найцінніші події
існували в коді й не існували в реальності. Друга: плитка не має права зеленіти
посеред інциденту — статус провайдера, прибитий цвяхом до «ok», бреше саме тоді,
коли ви на нього дивитесь.
